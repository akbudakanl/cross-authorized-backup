# Vault Extension: Out-of-Band (OOB) Notification Routing

**Classification:** SECURITY VISIBILITY / ALERT ROUTING

The concept outlined in this document runs in parallel with many architectural decisions in the project and is **mandatory** for the healthy functioning of the security infrastructure. However, it is **not yet completed** and therefore has not been fully integrated into the Core master file.

**Integration Requirements:**
1. **System Definition:** The detection and notification systems must be well-defined within the project before full integration into the core master guide.
2. **Cross-Isolation Verification:** Before this extension can be merged into the master file, it must be strictly verified that:
   - The channel sending notifications to the **PC** is strictly inaccessible by any actor on the **Phone**.
   - The channel sending notifications to the **Phone** is strictly inaccessible by any actor on the **PC**.

## 1. The Visibility Paradox

In a Zero Trust architecture, if a device is compromised, relying on that same device to receive security alerts is a fundamental flaw. If an attacker gains access to the Phone, and security alerts regarding the Phone's Tailnet identity are delivered to an email address active on the Phone, the attacker can silently delete or suppress the alert before the user sees it.

To solve this, the Vault architecture dictates a strict **Cross-Routed Out-of-Band (OOB)** notification policy.

## 2. Unidirectional Passive Visibility

The notification endpoints must possess **zero write access** to the AWS infrastructure or Tailscale control plane. They are strictly passive sinks designed for visibility. "Single-click remediation" (e.g., putting a "Revoke Token" button in the alert) is explicitly rejected, as compromising the notification endpoint would then give the attacker destructive control over the backup infrastructure.

## 3. Recommended Implementation

To maintain strict compartmentalization, the alert destinations must be physically separated across the user's devices:

### A. PC Tailnet Alerts 
* **Routing:** Sent exclusively to the **Phone**.
* **Method:** A dedicated E-mail alias (e.g., `vault-pc-alerts@proton.com`) or a dedicated Telegram Bot.
* **Constraint:** This account MUST NOT be logged in on the PC. It must only exist on the Phone. Furthermore, this email must never be used as the root recovery email for the AWS or VPS provider accounts.

### B. Phone Tailnet Alerts
* **Routing:** Sent exclusively to the **PC**.
* **Method:** A separate, dedicated Telegram account/bot (using Telegram Desktop) or a separate E-mail client.
* **Constraint:** This account MUST NOT be logged in on the Phone. To avoid having a background daemon running constantly on the PC, the user may choose to only launch the Telegram Desktop client (or Mail client) as part of the automated backup script (e.g., `Start-Process Telegram` at script start, and `Stop-Process` at the end). This introduces a known, accepted delay (alerts queue up and are seen at the next backup), prioritizing endpoint cleanliness over instantaneous alerting.

## 4. Conclusion

By separating the notification sinks across devices, the architecture ensures that compromising one compartment (e.g., the Phone) does not blind the user to the alert generated by the AWS `VaultAuditWatch` lambda. The user is guaranteed to see the alert on their surviving device (the PC) during their next backup cycle.
